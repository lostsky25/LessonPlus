# Контракты операций

OpenAPI 3.0.3 для бизнес-операций до их реализации. Каталог лежит в `@lessonplus/contracts`, потому что это уже общий пакет внешних контрактов. Доменные классы сюда не переносятся.

Работающие маршруты каркаса сохранены в спецификации gateway и сервисов как `implemented`. Новых контроллеров нет: операции `designed` не отвечают успехом.

## Спецификации

| Файл | Что описывает |
| ---- | ------------- |
| [components.yaml](components.yaml) | Общие схемы, параметры, ошибки и примеры. Маршрутов нет |
| [gateway.yaml](gateway.yaml) | Внешний вход браузера, порт 3000 |
| [subscriptions.yaml](subscriptions.yaml) | Абонементы, порт 3001 |
| [schedule.yaml](schedule.yaml) | Расписание, порт 3002 |
| [attendance.yaml](attendance.yaml) | Посещения, порт 3003 |
| [transfers.yaml](transfers.yaml) | Переносы, порт 3004 |
| [notifications.yaml](notifications.yaml) | Чтение состояния доставки, порт 3005 |

Поле `payload` у `EventEnvelope` в TypeScript по-прежнему не задано. Входящие события перечислены расширением `x-accepted-events` и не добавляют HTTP-путей.

## Статус реализации

У каждой операции есть `x-implementation-status`:

| Значение | Смысл |
| -------- | ----- |
| `implemented` | Маршрут уже есть в NestJS. Это `GET /health/live`, `GET /health/ready` и gateway `GET /api/system/status` |
| `designed` | Контракт для следующей реализации. Контроллера нет, успешный ответ не имитируется |

Авторизация тоже проектируется. Схема `bearerAuth` описана, но JWT в каркасе нет, и сейчас эти ответы 401 и 403 не возвращаются.

## Версионирование

`info.version` всех файлов — `0.1.0`, как у уже работающего Swagger.

Реализованные health и `/api/system/status` остаются без версии в пути: они уже опубликованы.

Проектируемые бизнес-пути используют `/v1`.

- Ломающее изменение — удаление или переименование поля, смена типа, новый элемент `enum`, другая семантика кода ответа, другая область ключа идемпотентности. Для него заводится `/v2` новым файлом, старый файл остаётся.
- Добавление необязательного поля или новой операции повышает `info.version` внутри `/v1` и путь не меняет.
- Пример числа, срока или вместимости требованием не становится.

## Граница gateway и сервисов

Браузер вызывает только gateway: `/health`, `/api/system/status` и проектируемые `/api/v1/...`.

Сервис владельца публикует тот же контракт на `/v1/...`. Связь записана в `x-upstream` у gateway и в `x-gateway-path` у сервиса.

`/internal/v1` не проксируется. Его вызывает сервис `transfers` от своего имени:

| Вызов | Назначение |
| ----- | ---------- |
| `POST /internal/v1/rights/{rightId}/reservations` | Заблокировать неиспользованное право |
| `POST /internal/v1/rights/{rightId}/reservations/{reservationId}/releases` | Снять блокировку до новой привязки |
| `POST /internal/v1/rights/{rightId}/rebindings` | Зафиксировать новую привязку |
| `POST /internal/v1/lessons/{lessonId}/seat-reservations` | Зарезервировать целевое место и выдать `targetBookingId` |
| `POST /internal/v1/seat-reservations/{reservationId}/releases` | Снять резерв места до новой привязки |
| `POST /internal/v1/transfers/{transferId}/booking-confirmations` | Подтвердить уже выданную запись, привязку не создавать |
| `POST /internal/v1/bookings/{bookingId}/transfer-releases` | Освободить исходное место, новую привязку не снимать |

Прямое чтение чужих таблиц запрещено. Списание права — событие `AttendanceRegistrationRequested`, не HTTP-клиент посещений.

При проксировании `/api/v1` в `/v1` gateway передаёт исходный `Idempotency-Key` без изменения и сохраняет исходную идентичность вызывающего. Идентичность gateway ключ не заменяет. Внутренние вызовы таблицы выше идут от роли `transfers`: у каждого шага свой ключ, стабильный при повторе этого шага одной заявки и не равный публичному ключу заявки.

## Ошибки

Проектируемое тело — схема `Error`: `type`, `title`, `status`, `code`, `detail`. Необязательны `instance`, `correlationId`, `reason` и `errors`.

| Код | HTTP | Когда |
| --- | ---- | ----- |
| `invalid_request` | 400 | Форма тела, параметр, курсор или нарушение ограничения вроде `endsAt` позже `startsAt` |
| `unauthorized` | 401 | Нет учётных данных. Проектируется |
| `forbidden` | 403 | Роль не допущена. Проектируется |
| `not_found` | 404 | У владельца нет такого объекта |
| `state_conflict` | 409 | Объект есть, но операция противоречит состоянию. Уточнение — `reason` |
| `idempotency_key_reused` | 409 | Тот же ключ уже сохранён с другим отпечатком: другим телом, другими path-параметрами или другими значимыми query |
| `dependency_unavailable` | 503 | Недоступна своя база или зависимость, без которой шаг нельзя принять |

Работающий фильтр NestJS к этому контракту не приведён. Необработанная ошибка каркаса по-прежнему `{ "statusCode": 500, "message": "Внутренняя ошибка сервера" }`. Неготовые PostgreSQL или RabbitMQ бизнес-сервиса по-прежнему отвечают 503 телом readiness, не схемой `Error`.

Запись, регистрация посещения и перенос отвечают `202` схемой `AcceptedOperation`. `accepted` не означает занятое место, окончательную отметку или выполненный перенос. Дальнейшее состояние читается `statusUrl`.

Отмена школой, обычная отмена записи и исправление посещения отвечают `202` телом своей операции: `status: accepted`, эффекты `pending`, `failureReason: null` и `statusUrl` на GET этой операции. Идентификатор операции в `id` и в `statusUrl` совпадает. Повторный GET того же пути показывает прогресс именно этого запроса:

| Запрос | Чтение |
| ------ | ------ |
| `POST /api/v1/lessons/{lessonId}/school-cancellations` | `GET /api/v1/school-cancellations/{schoolCancellationId}` |
| `POST /api/v1/bookings/{bookingId}/cancellations` | `GET /api/v1/booking-cancellations/{bookingCancellationId}` |
| `POST /api/v1/attendances/{attendanceId}/corrections` | `GET /api/v1/attendance-corrections/{attendanceCorrectionId}` |

У операции статусы `accepted` (этот запрос ждёт), `in_progress`, `completed` и `rejected`. `rejected` заполняет `failureReason`. GET занятия, записи или отметки этот запрос не заменяет: там виден чужой или прежний итог. Отмена школой получает `completed` только когда `lessonEffect` равен `canceled`, `rightEffect` равен `preserved` и `transferLimitEffect` равен `not_spent`. Статус занятия `canceled_by_school` этого не заменяет. Неуспех доставки уведомления операцию не завершает и не отменяет.

## Идемпотентность

Заголовок `Idempotency-Key` обязателен для проектируемых POST и PATCH.

Область ключа — исходная вызывающая сторона, метод и шаблон пути владельца (`/v1/...`, без префикса `/api`). Отпечаток — фактические значения path-параметров, значимые query-параметры операции и канонический JSON тела. Канонический JSON записан без незначимых пробелов, ключи объектов идут по возрастанию кодов Unicode. Сам заголовок в отпечаток не входит. Query-параметр значим, если он объявлен у операции.

Тот же ключ и тот же отпечаток возвращают сохранённый ответ, включая исходный код. Тот же ключ и другой отпечаток — `409 idempotency_key_reused`. В том числе одинаковые ключ и тело `PATCH /v1/lessons/A` и `PATCH /v1/lessons/B` конфликтуют: идентификаторы в пути различны. Пример такого ответа — `differentResource` в компоненте `Conflict`.

Gateway проксирует публичную операцию, передавая ключ без изменения и сохраняя идентичность исходного вызывающего. Идентичность gateway ключ не заменяет, и второй ключ для того же публичного вызова не создаётся. Сохранённый ответ принадлежит владельцу.

Каждый внутренний шаг `transfers` получает свой ключ. Он стабилен при повторе этого шага одной заявки, не равен публичному ключу заявки и не равен ключу другого шага. Повтор события с тем же `event_id` по-прежнему не списывает право второй раз; это отдельное правило потребителя, не HTTP-ключ.

## Роли

Роли заданы `x-required-roles` и пока не проверяются.

| Роль | Операции |
| ---- | -------- |
| `administrator` | Активация и просмотр абонементов и прав, расписание, создание и изменение занятия, отмена школой и её прогресс, запись, список записей занятия и отмена записи с её прогрессом, просмотр регистрации, отметки и исправления, просмотр переносов, чтение доставки |
| `teacher` | Просмотр расписания и записей занятия, регистрация посещения, исправление отметки и просмотр регистрации, отметки и этого исправления, чтение доставки |
| `parent` | Просмотр своего абонемента и прав, просмотр расписания, запись на занятие, просмотр своей записи, отмена этой записи и её прогресс, заявка на перенос и её результат, чтение доставки |
| `transfers` | Только внутренние вызовы к абонементам и расписанию |

## Списки

Курсорная пагинация. `limit` от 1 до 100, по умолчанию 20. `nextCursor: null` заканчивает список. Сортировка — поле ответа; ведущий `-` означает убывание. Значение по умолчанию указано у параметра `sort`.

Чтение `freeSeatCount` место не удерживает.

## Решения, которые ещё зависят от хранения

- Где у тарифа лежат размер остатка, срок действия, лимит переносов и срок уведомления. В контракте это параметры, не числа.
- Кто переводит абонемент в `expired`: отдельного внешнего метода нет.
- Списывает ли отсутствие право. Пока для него `rightEffect: unspecified`.
- Восстанавливается ли право при исправлении присутствия на отсутствие. Завершённое исправление может сохранить `rightEffect: unspecified` и восстановление не обещает.
- Как владелец операции отмены школой узнаёт `rightEffect` и `transferLimitEffect`, а владелец отмены записи — `rightBindingEffect`, не читая чужие таблицы. Отдельных имён событий для этих флагов в каталоге нет. Пока флаги `pending`, статус операции не бывает `completed`.
- Как связать будущего пользователя с учеником. Контакт родителя принадлежит абонементам, учётной записи ещё нет.
- Создание ученика, тарифа, преподавателя и группы в этот срез не входит. Активация и занятие только ссылаются на их идентификаторы.
- Срок хранения ключа идемпотентности.
- Отдельное поле времени создания права и записи. До него сортировка этих списков идёт по `id`.
