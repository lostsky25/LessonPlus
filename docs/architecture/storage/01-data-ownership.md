# Владение данными

Шаг 6.1 архитектуры хранения. Границы сервисов, C4, OpenAPI, контракты событий и карта взаимодействий уже зафиксированы. Этот документ не меняет пути, схемы и имена фактов.

Пометки: **существует** — есть в Prisma и миграциях; **проектируется** — решение для следующей реализации, таблиц и CRUD нет.

Сейчас в каждой схеме только `outbox_events` и `processed_events`. Бизнес-сущности ниже все **проектируются**. Gateway, `@lessonplus/contracts` и `@lessonplus/config` сущностями не владеют.

Владельцы совпадают с [domain.md](../domain.md). Чтение и согласование — с [interactions.md](../interactions.md) и OpenAPI. Экземпляр PostgreSQL, роли и проверяемая изоляция схем — в [02-storage-and-isolation.md](02-storage-and-isolation.md). Проектируемые таблицы — в [03-data-model.md](03-data-model.md).

## Правила

- У каждого изменения один сервис-владелец. Остальные передают команду или применяют факт, но чужой остаток, место и отметку не пишут.
- Прямые `INSERT`/`UPDATE`/`DELETE` в чужую схему, внешние ключи PostgreSQL через границу схем и SQL `JOIN` между схемами **запрещены**. Один экземпляр `postgres:17.11`, база `lessonplus`, пять схем и пять ролей из `infra/postgres/init/001-roles.sh`: роль сервиса авторизована только на свою схему.
- Межсервисная ссылка — UUID, выданный владельцем. Это не внешний ключ и не право читать чужую строку.
- Первичные данные живут у владельца. У потребителя допустимы идентификатор и собственное состояние процесса. Второй справочник той же сущности не заводится.
- Копия для чтения не становится источником истины: конфликт разрешает владелец, а не проекция.

## Справочники

Отдельный сервис людей, CRM или общих справочников не вводится: в репозитории пять бизнес-сервисов, CRM за границей этапа.

| Справочник | Владелец | Схема | Почему | Первичные данные | Копии |
| ---------- | -------- | ----- | ------ | ---------------- | ----- |
| Ученик и контакт родителя | `subscriptions` | `subscriptions` | Абонемент и право существуют до первой записи. Родитель видит остаток у абонементов, а не у занятия | Карточка ученика и контакт | В других сервисах только `studentId` |
| Тариф | `subscriptions` | `subscriptions` | Ответственность сервиса уже в README и C4. Размер остатка, срок, лимит переносов — параметры тарифа, не числа контракта | Параметры продукта | Каталога тарифов у координатора нет |
| Преподаватель | `schedule` | `schedule` | Ведёт группу и занятие. Другому сервису справочник не нужен | Карточка преподавателя | `teacherId` только в расписании |
| Группа | `schedule` | `schedule` | Состав расписания, не абонемента | Группа | `groupId` только в расписании |
| Правило переноса | `transfers` | `transfers` | Координатор применяет правило, не владея правом и местом | Как оценивать срок уведомления и что отмена школой лимит не тратит | Не копия тарифа |
| Канал доставки | `notifications` | `notifications` | Доставка не входит в транзакцию абонемента, записи или переноса | Сейчас только `imitation` | Нет |

**Допущение.** Контакт родителя — атрибуты ученика в `subscriptions`, не отдельная сущность и не отдельный сервис. Учётной записи пользователя ещё нет: связать будущего субъекта JWT с `studentId` контракты не задают.

**Допущение.** Создание ученика, тарифа, преподавателя и группы в текущий срез OpenAPI не входит. Активация и занятие только ссылаются на уже известные UUID. Откуда идентификаторы появляются до первой активации — следующий срез хранения, не новый сервис.

### Право на занятие и журнал операций

| | |
| --- | --- |
| Сервис-владелец | `subscriptions` |
| Источник истины | Схема `subscriptions`. Состояние — `LessonRight` (`available`, `reserved`, `bound`, `consumed`). Резерв права — `RightReservation`. Журнал операций права — внутренняя история владельца, публичного ресурса нет |
| Разрешённые изменения | Только абонементы: резерв `POST /internal/v1/rights/{rightId}/reservations`, снятие `.../releases`, перепривязка `POST /internal/v1/rights/{rightId}/rebindings`, списание по `AttendanceRegistrationRequested`, восстановление при исправлении. Чужой сервис остаток не меняет |
| Потребители | `transfers` — резерв, снятие, перепривязка; `attendance` — `LessonRightConsumed` / `LessonRightRestored`; `schedule` — `LessonRightTransferred` (узнать о commit, не писать право); `notifications` — факты списания и восстановления |
| Чтение | `GET /v1/subscriptions/{subscriptionId}/rights`, `GET /v1/rights/{rightId}`. Привязка **не** входит в `Booking`. Журнал снаружи не читают |
| Внешние идентификаторы | `rightId`, `subscriptionId`, `studentId`; при `bound` — `bookingId`; при `reserved` — `transferId`; у резерва — `reservationId`, `sourceBookingId` |
| Локальные проекции | У «Переносов» — `reservationId` права и признак **commit привязки** в заявке (не «получили HTTP 200»). У «Посещений» — `rightId` отметки. У «Расписания» на записи хранится `rightId` как ссылка места, не как действующая привязка |

Инварианты владельца: одна действующая привязка; `bookingId` задан только при `bound`; `transferId` задан только при `reserved`; списание присутствия не чаще одного раза на `(rightId, bookingId)`; сериализация переноса и списания на `rightId`.

Журнал пишется в той же транзакции, что изменение права и строка outbox. Он не заменяет 20 фактов каталога и не читается SQL из другой схемы.

### Запись

| | |
| --- | --- |
| Сервис-владелец | `schedule` |
| Источник истины | Схема `schedule`, ресурс `Booking` (`seatStatus`: `pending`, `confirmed`, `canceled`, `rejected`) |
| Разрешённые изменения | Обычная запись `POST /v1/lessons/{lessonId}/bookings`; подтверждение места в переносе `POST /internal/v1/transfers/{transferId}/booking-confirmations`; обычная отмена `POST /v1/bookings/{bookingId}/cancellations`; освобождение исходного места `POST /internal/v1/bookings/{bookingId}/transfer-releases`. Привязку права эти вызовы не создают и (для transfer-release) не снимают |
| Потребители | Как в `catalog.json`. `BookingConfirmed` ordinary (`transferId=null`): `transfers`, `subscriptions`, `notifications`. `BookingConfirmed` в переносе: `transfers`. `BookingCanceled` ordinary: `subscriptions`, `notifications`. `BookingCanceled` `cause=transfer_source_release`: `transfers` |
| Чтение | `GET /v1/bookings/{bookingId}`, список записей занятия. Gateway `Booking` и `LessonRight` не склеивает |
| Внешние идентификаторы | `bookingId`, `lessonId`, `studentId`, `rightId` |
| Локальные проекции | У права — действующий `bookingId` (привязка). У отметки и заявки — ссылка на запись. Это не второй `Booking` |

Успешная обычная запись — подтверждённое место **и** подтверждённая привязка у абонементов. Место `confirmed` при отказе привязки успешной записью не считается. Протокол освобождения такого места существующими контрактами не задан: состояния хранят порознь.

Операция `BookingCancellation` принадлежит расписанию. `rightBindingEffect` заполняет владелец места, не абонементы; сигнала без чужой схемы нет.

### Заявка на перенос и состояние процесса

| | |
| --- | --- |
| Сервис-владелец | `transfers` |
| Источник истины | Схема `transfers`, ресурс `Transfer` плюс координаторское состояние шагов |
| Разрешённые изменения | Принять `POST /v1/transfers`; вести шаги HTTP к владельцам; `completed` только после commit привязки, подтверждения новой записи и освобождения источника; `rejected` только до commit. После commit компенсация и `rejected` запрещены безусловно |
| Потребители | `TransferRequested` получают `schedule`, `subscriptions` и `notifications`; сами по событию не резервируют. Итог отдельно: `notifications` — `TransferCompleted` / `TransferRejected` |

| Локальные проекции | Обязательное состояние процесса: текущий шаг, `reservationId` права, `reservationId` места, `targetBookingId`, признак commit привязки. Это не копия `LessonRight` и не копия `Booking` |

## Межсервисные ссылки

Ссылка — UUID в поле потребителя. Согласование — повтор того же `Idempotency-Key` или применение факта по `event_id` в `processed_events`. SQL по чужой схеме не используется, даже если оба процесса смотрят на один PostgreSQL.

| UUID | Кто выдаёт | Кто хранит как ссылку | Согласование |
| ---- | ---------- | --------------------- | ------------ |
| `studentId` | `subscriptions` | schedule, attendance, transfers, notifications | Форма — UUID контракта, не существование карточки. Первичную карточку знает только `subscriptions`. Другие сервисы не проверяют её SQL и не выводят «ученик есть» из одного UUID. Можно сверить совпадение `studentId` у права (`GET /v1/rights/{rightId}`, поля команд и фактов). Проверка самой карточки без Student GET/события не закрыта |
| `tariffId` | `subscriptions` | только подписка у владельца | Чужие сервисы тариф не читают |
| `subscriptionId` | `subscriptions` | право у владельца | Истечение — факт `SubscriptionExpired`, не SELECT из `transfers` |
| `rightId` | `subscriptions` | Booking, SeatReservation, Attendance, Transfer | Сверка `studentId`/`lessonId`/`rightId` при обработке у владельца права или отметки, не JSON Schema |
| `bookingId` | `schedule` | LessonRight (привязка), Attendance, Transfer (`sourceBookingId` / `targetBookingId`) | Снимать привязку только если она ещё на этот `bookingId` |
| `lessonId` | `schedule` | Attendance, Transfer (`targetLessonId`), SchoolCancellation | Отмена школой — факт, не JOIN занятия |
| `transferId` | `transfers` | RightReservation, SeatReservation, факты шагов | Ключи внутренних HTTP ≠ публичный ключ заявки |
| `reservationId` права | `subscriptions` | состояние заявки у transfers | Нужен из подтверждённого 201; таймаут ≠ отсутствие резерва |
| `reservationId` места | `schedule` | состояние заявки у transfers | Тот же принцип; запоздалый release целевого резерва — отдельная гонка |
| `registrationId` | `attendance` | payload списания / восстановления | Не ключ списания |
| `attendanceId` | `attendance` | исправление | Одна отметка на `bookingId` |
| `notificationId` | `notifications` | нет чужих писателей | Нет |

Запрещено: `REFERENCES` на таблицу другой схемы; представление, которое читает две схемы; роль сервиса с `USAGE` на чужую схему; gateway с `DATABASE_URL`.

## Проверка сценариев

У каждого изменения ниже один писатель.

### Активация

Администратор `POST /v1/subscriptions`. Пишет только `subscriptions`: абонемент, права, журнал, outbox. `SubscriptionActivated` не создаёт занятие и не занимает место. «Уведомления» пишут только своё поручение. Ученик и тариф уже должны существовать у того же владельца.

### Обычная запись

«Расписание» пишет место (`Booking`, вместимость). «Абонементы» пишут привязку права только по `BookingConfirmed` с `transferId=null`. Два изменения — два владельца. Подтверждённое место без привязки не есть успешная запись.

### Посещение

«Посещения» пишут регистрацию. «Абонементы» пишут списание. «Посещения» пишут окончательную отметку после `LessonRightConsumed`. «Уведомления» пишут доставку. Остаток меняет только первый владелец права.

### Перенос

«Переносы» пишут заявку и шаги процесса. «Абонементы» пишут резерв права и commit привязки. «Расписание» пишет резерв целевого места, подтверждение новой записи и освобождение исходного места. После commit компенсацию не запускает никто, в том числе по чужому `4xx`.

### Отмена школой

«Расписание» пишет статус занятия и операцию `SchoolCancellation`. «Абонементы» сохраняют право, не уничтожая его. «Переносы» не тратят пользовательский лимит. «Посещения» не проводят это как пользовательский перенос. «Уведомления» не влияют на `completed`.

## Связь с контрактами и C4

| Уже принято | Этот документ |
| ----------- | ------------- |
| C4: координатор ходит HTTP к владельцу, чужие таблицы не читает | Повторено запретом JOIN/FK |
| Только абонементы меняют право | Таблицы права, журнала и резерва права |
| Только расписание выделяет места | Занятие, запись, резерв места |
| Переносы координируют | Заявка и состояние процесса, не остаток и не вместимость |
| Посещения инициируют списание событием | Нет HTTP-клиента attendance → subscriptions |
| Уведомления независимы | Нет каскадного отката |
| `LessonRightTransferred` не закрывает TTL | Владелец места остаётся schedule; протокол protection/expiry/release не закрыт |

Новых маршрутов и 21-го события здесь нет.

## Что существует и что только спроектировано

**Существует** (не бизнес-сущности): схемы `subscriptions`, `schedule`, `attendance`, `transfers`, `notifications`; роли `*_user`; таблицы `outbox_events` и `processed_events` в миграциях `20261007120000_init`.

**Только спроектированы:** ученик и контакт, тариф, абонемент, право, журнал операций права, резерв права, преподаватель, группа, занятие, запись, резерв места, операции отмены школой и обычной отмены записи, регистрация и отметка посещения, исправление, заявка и правило переноса, координаторское состояние шагов, уведомление, попытка доставки.

## Допущения

1. Справочник учеников и контактов — у `subscriptions`, без второго каталога и без сервиса CRM.
2. Контакт родителя не выделяется в отдельную таблицу-сущность за границей ученика.
3. Преподаватель и группа — только `schedule`.
4. Журнал операций права и попытки доставки внутренние: публичных GET для них в текущем OpenAPI нет.
5. Проекция — идентификатор или поле процесса координатора, не копия агрегата владельца.
6. Параметры тарифа (размер пакета, срок, лимит переносов) хранит владелец тарифа. Координатор не заводит зеркало тарифа.

## Открытые вопросы

Не закрываются этим шагом и не порождают новых фактов:

1. Как «Расписание» узнаёт `rightEffect` и `transferLimitEffect` для `completed` отмены школой без чужой схемы.
2. Как владелец обычной отмены записи узнаёт `rightBindingEffect`.
3. Списывает ли отсутствие право; восстанавливается ли право при смене присутствия на отсутствие.
4. Кто и каким таймером переводит абонемент в `expired`.
5. Как «Переносы» применяют параметры лимита и срока уведомления тарифа, не читая схему абонементов и не расширяя payload версии 1.
6. Протокол protection / expiry / release целевого резерва после commit `rebindings`.
7. Обычная запись: место confirmed, привязка отклонена — освобождение места.
8. Срок хранения `Idempotency-Key` и TTL резерва места **до** commit.
9. Создание ученика, тарифа, преподавателя и группы, связь учётной записи с `studentId`.
10. Нет факта «списание отклонено».
11. Как потребитель, не читающий схему абонементов, подтверждает существование карточки ученика: Student GET и события ученика в контрактах нет; совпадение `studentId` у права карточку не заменяет.
