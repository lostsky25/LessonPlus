# Архитектура

Система учёта абонементов и переносов занятий для учебного центра. Этот документ фиксирует границы сервисов и правила, которые следующая реализация должна сохранить.

## Ответственность

| Сервис        | Ответственность                                                       |
| ------------- | --------------------------------------------------------------------- |
| subscriptions | Тарифы, абонементы, права на занятия, резервирование и списание       |
| schedule      | Группы, занятия, вместимость, записи и резервы мест                   |
| attendance    | Отметки присутствия и отсутствия                                      |
| transfers     | Заявки, правила и координация переноса                                |
| notifications | Уведомления и результаты доставки                                     |
| api-gateway   | Вход для интерфейса. Бизнес-правил нет и доступа к базам сервисов нет |

Посещение расходует одно право на занятие. Перенос зависит от тарифа, срока уведомления и наличия места. Отмена школой сохраняет занятие.

## Направление зависимостей

Внутри бизнес-сервиса:

1. Domain — чистый TypeScript. Не зависит от NestJS, Prisma, RabbitMQ и HTTP DTO.
2. Application — сценарии и порты. Зависит от Domain и от собственных интерфейсов.
3. Infrastructure — реализует порты.
4. Presentation — вызывает прикладные сценарии.
5. Composition root NestJS связывает реализации с портами.

Сервисы не импортируют внутренние файлы друг друга и не читают чужие таблицы. Общий пакет `@lessonplus/contracts` содержит только внешние DTO, типы и контракты событий. Доменные модели в него не выносятся. `@lessonplus/config` проверяет переменные окружения и тоже не содержит домена.

У каждого сервиса своя схема PostgreSQL, свой пользователь и свой каталог Prisma. Генерация клиента пишет результат в `src/generated/prisma` этого сервиса.

## Правила будущей реализации

- Одно право имеет только одну действующую привязку к записи.
- Повтор одного события не вызывает второго списания.
- Остаток занятий не становится отрицательным.
- Вместимость учитывает подтверждённые записи и действующие резервы.
- Отмена школой сохраняет право и не расходует лимит пользовательских переносов.
- Перенос и списание одного права требуют защиты от конкурирующих операций.

## Что сознательно ещё не работает

Следующие механизмы описаны как план, а не как текущее поведение:

- **Transactional outbox.** Таблицы `outbox_events` и `processed_events` уже создаются. Порты записи и учёта обработанных идентификаторов есть. Диспетчер, который публикует строки outbox в RabbitMQ, на этом этапе не запускается.
- **Идемпотентность потребителей.** Уникальный идентификатор в `processed_events` подготовлен для того, чтобы повтор доставки не выполнял сценарий второй раз. Самих потребителей бизнес-событий нет.
- **Saga переноса.** Перенос затрагивает subscriptions, schedule и transfers. Оркестрация шагов, компенсации и защита от гонки переноса со списанием будут отдельным этапом. Сейчас заявка на перенос не создаётся и событие списания не публикуется.

Каталог имён событий лежит в `@lessonplus/contracts`. Поля `payload` будут уточнены вместе со сценариями.
